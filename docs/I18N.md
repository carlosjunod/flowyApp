# Internationalization (native)

FlowyApp ships English and Spanish. This document is the operating guide for
changing copy, adding a key, or touching the cross-platform presentation
contracts.

## What is translated, and what is not

| Translated | Left alone |
| --- | --- |
| Every label, button, placeholder, alert, empty state and accessibility label | Item titles, notes, tags, categories — the user's own words |
| Generated captions like "Primary source" or "Deep Dive" | AI output: summaries, transcripts, digest bullets, chat answers |
| Error *sentences* | Error **codes** (`ORIGINAL_REQUIRED`, `CHAT_BUSY`), `item.type` enums, URLs, API field names |
| The digest-chat seed draft (editable text the user reviews before sending) | Stored conversation titles, including the `New conversation` sentinel |
| Product copy around brand names | Brand names themselves: Flowy, YouTube, Instagram, Anthropic, OpenAI, Voyage AI |

Two literals are deliberately **never** translated because a server compares
them byte-for-byte:

- `delete my account` — the account-deletion confirmation phrase.
- `New conversation` — `DEFAULT_CONVERSATION_TITLE`, which is persisted and
  synced across devices. The UI recognises the sentinel and renders
  `chat.history.newConversation` instead.

## Layout

```
src/lib/i18n/
  locale.ts            negotiation primitives (pure, no React, no RN)
  dictionary.ts        dictionary shape + the compile-time key union
  translate.ts         lookup + interpolation + plurals + fallback
  format.ts            dates, numbers, relative time, byte sizes
  device.ts            device language detection (RN-specific)
  storage.ts           persistence through the local secure store
  LocaleProvider.tsx   the provider, useI18n(), useTranslate()
  index.ts             the only entry point components import
  dictionaries/
    en/{common,auth,app,inbox,chat,digest,settings}.ts
    es/{…the same modules…}
```

`locale.ts`, `dictionary.ts`, `translate.ts` and `format.ts` are native-owned
copies of the equivalent modules in the Flowy server repo
(`apps/web/lib/i18n/`). They are **copied, not imported**: the Expo bundler has
to build this app on its own, and a cross-repo runtime import would break that.
Keep the two behaviourally identical when either changes.

## Adding or changing copy

1. Add the key to the English module. It is the schema — `Dictionary = typeof
   en` — so this is what defines the key's existence and shape.
2. Add the same key to the Spanish module. `npm run typecheck` fails if you
   forget: `const es: Dictionary['…']` makes a missing or misspelled key a
   compile error rather than a silent English string on a Spanish screen.
3. Use it as `t('namespace.key')` or, for a computed key, `tKey(someKey)`.

There is deliberately **no `as const`** anywhere in the English dictionary.
`as const` would infer literal string types and force the Spanish file to repeat
the English text verbatim; plain inference widens leaves to `string`, which is
what lets the Spanish file type-check as a *translation*.

### Plurals and placeholders

```ts
count: { one: '{count} item', other: '{count} items' }
```

`one`/`other` are required. `zero` is optional and wins at 0 when present —
"No saved items" reads better than "0 saved items", and keeping it in the
dictionary keeps it translatable. `Intl.PluralRules` is optional on Hermes, so
`selectPluralForm` falls back to `count === 1 ? one : other`; for English and
Spanish that fallback is exact, not an approximation.

Placeholders are `{name}`. Numeric values are formatted through
`Intl.NumberFormat`, so `{count}` renders `1,250` in English and `1.250` in
Spanish. A missing value renders the literal `{name}` rather than a gap, so QA
sees it.

## Locale policy

1. An explicit choice, persisted under `flowy.locale` in the device's **local**
   secure store, always wins.
2. Otherwise the device's language preferences are negotiated. Any Spanish
   variant — `es`, `es-419`, `es-MX`, `es_CO` — resolves to `es`.
3. Otherwise English.

Detection is never persisted. Only an explicit choice writes storage, which is
what keeps "explicit choice wins" meaningful: someone who later changes their
phone's language is not pinned to a locale they never picked.

Selecting **Automatic** deletes the stored row. Without the delete, the next
launch would read the previous explicit locale back and quietly re-pin the user.

### Detection sources

Ordered, best first:

1. **iOS** — `Settings.get('AppleLanguages')`, an *ordered* list. Ordering is
   why this comes before `Intl`: a phone set to Spanish-then-English must
   resolve to Spanish, and only an ordered list can express that.
2. **Android** — `I18nManager.getConstants().localeIdentifier` (`es_MX`).
3. **Web** — `navigator.languages` / `navigator.language`.
4. **Any** — `Intl.DateTimeFormat().resolvedOptions().locale`.

Each native source is read three ways — the public JS API, then
`getConstants()`, then the legacy own-property. React Native 0.81 moved both
modules behind TurboModule getters, so reading `NativeModules.SettingsManager
.settings` directly returns `undefined` there, which silently dropped the
ordered iOS list and left only the `Intl` fallback.

This app adds **no localization dependency**: `expo-localization` and friends
stay out of `package.json`.

### Startup order

1. The first render resolves the device language *synchronously*. Reading the
   secure store is asynchronous, and gating the first frame on it would mean a
   blank screen or a visible English flash on a Spanish phone.
2. The persisted choice is read after mount and applied if present. A failed
   read degrades to the detected language — it never blocks or crashes boot.
3. If the user picks a language *or picks Automatic* while that read is in
   flight, the hydration result is discarded. The guard is a counter rather than
   a boolean because Automatic is a choice too.
4. Persistence is serialised through one promise chain, so a write followed by a
   delete cannot land out of order.

## Cross-platform presentation contracts

Four modules are mirrored **byte-for-byte** with the web client and return
translation *keys* rather than sentences, so one copy of the logic serves both
platforms:

| Module | Emits keys under |
| --- | --- |
| `src/types/inbox-presentation.ts` | `inbox.status.*` |
| `src/types/reader.ts` | `inbox.reader.*` |
| `src/types/semantic.ts` (the "Localisable variants" block) | `inbox.semantic.*` |
| `src/hooks/useChatEngine.ts` (`chatErrorKey`) | `chat.errors.*` |

Renaming one of those keys on either side is a breaking change for the other.
`npm run test:i18n-parity` renders every key these contracts can emit, in both
locales, with no English fallback — so a rename fails there rather than at
runtime.

`src/types/semantic.ts` keeps its English `semanticCoverageMessage` /
`semanticEvidenceLabel` functions untouched: the worker calls them to write
`exploration.notes`, which is **stored content** and must not change shape or
language. The key-returning variants sit beside them.

## The digest report language is separate (D-041)

`DigestPreferences.locale` is a server-side AI generation setting: the language
Flowy *writes your reports in*. It is configured on the digest settings screen
and is never changed by the interface language. `test:i18n-parity` asserts that
the digest screen never calls `setLocale` and that the provider never touches
digest preferences.

## Tests

| Command | What it covers |
| --- | --- |
| `npm run typecheck` | The real parity gate: EN/ES shape equality |
| `npm run test:i18n-core` | Negotiation, device detection across RN module shapes, persistence, translator, formatters |
| `npm run test:i18n-parity` | Same key sets, no empty strings, placeholder/plural parity, every contract-emitted key resolves in both locales, D-041 |
| `npm run test:i18n-screens` | `LocaleProvider` startup/race/persistence, and the auth screens rendering real Spanish |
| `npm run test:i18n` | All three |

The scripts use the same transpile-and-mock loader as
`test-reader-navigation.cjs`. Nothing touches a device, a keychain or a network.

One loader detail worth keeping: module resolution stats each candidate and
accepts only a regular file. `src/lib/i18n/dictionaries/en` exists as a
*directory*, so a bare `existsSync` check picks it and `readFileSync` fails with
`EISDIR`.
